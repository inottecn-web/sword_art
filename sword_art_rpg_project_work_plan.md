# Sword Art RPG — полный план работы над проектом

## 0. Назначение документа

Этот документ описывает полный поэтапный план работы над **Sword Art RPG**: от текущих дизайн-документов до MVP, закрытого теста, публичной беты, запуска первого этажа и дальнейшего масштабирования башни.

План опирается на уже созданные документы:

- `sword_art_rpg_ultimate_concept.md` — концепция игры, первый этаж, классы, d6, PvP, экономика, ИИ-слой;
- `sword_art_rpg_technical_specification.md` — архитектура, server-authoritative модель, Rules Engine, AI Orchestrator, event log, ledger, API, деплой;
- `sword_art_rpg_deep_research_brief.md` — вопросы для интернет-исследования перед сложными техническими решениями;
- `sword_art_rpg_codex_uiux_brief.md` — UI/UX-бриф для Codex и будущих макетов.

Главная цель плана — превратить концепт в управляемый backlog с фазами, результатами, критериями готовности и зависимостями.

# 1. Главные принципы разработки

## 1.1. Product principles

1. **Сначала вертикальный срез, потом масштабирование.** Не строить сразу 100 этажей, рынок, гильдейские войны и эндгейм. Сначала доказать, что один маленький игровой цикл работает.
2. **Сервер всегда авторитетен.** Клиент не решает исходы, не выдаёт предметы и не меняет состояние мира.
3. **ИИ не управляет правилами.** ИИ описывает уже рассчитанный результат, но не создаёт награды, не меняет бой, экономику или PvP.
4. **Первый этаж — миниатюра всей игры.** Он должен показать безопасную зону, исследование, сбор, крафт, PvE, мягкий PvP-риск, социальность, фракции и подготовку к боссу.
5. **Документы живут вместе с кодом.** Любое изменение архитектуры, экономики, классов или UX должно обновлять соответствующий MD-файл.
6. **Баланс проверяется симуляциями.** Нельзя балансировать d6, классы, PvP и экономику только на ощущениях.
7. **Live-ops закладывается заранее.** Хроника, event log, ledger, админка, observability и модерация нужны до публичного теста, а не после скандала.

## 1.2. Definition of Done для любой фичи

Фича считается готовой только если:

- есть описание поведения и edge cases;
- есть серверная валидация;
- есть UI-состояния: loading, success, error, disabled, reconnect;
- есть логирование важных событий;
- есть тесты на критичные инварианты;
- есть миграции/seed-данные, если нужны;
- есть базовая документация;
- проверено, что ИИ не может изменить системный результат;
- проверено, что повтор запроса не дублирует награды или списания.

## 3.1. Цель

  - безопасная LLM-интеграция;
  - realtime-стек;
  - ledger/антидюп;
  - Rules Engine / encounter state;
  - content pipeline;
  - observability/replay-аудит.
- Сравнить варианты и выбрать решения для MVP.
- Обновить техническую спецификацию по результатам исследования.
- Зафиксировать ADR по ключевым решениям.
- Сформировать риск-реестр проекта.

## 3.3. Deliverables

- Отчёт Deep Research.
- Обновлённый `sword_art_rpg_technical_specification.md`.
- ADR-файлы или раздел ADR в спецификации.
- Таблица рисков: вероятность, ущерб, mitigation.
- Черновой MVP backlog.

## 3.4. Критерии завершения

- Выбран realtime-подход для MVP.
- Выбран подход к LLM structured output и safety validation.
- Выбран подход к ledger и антидюпу.
- Понятно, пишется ли Rules Engine полностью вручную или используются библиотеки.
- Понятно, где хранится контент MVP: YAML/JSON, БД, гибрид.

# 6. Фаза 3 — Core gameplay vertical slice

## 6.1. Цель

Доказать основной gameplay loop в минимальном виде.

Минимальный цикл:

> персонаж → сцена → список действий → выбор действия → серверная проверка → d6 → результат → event log → UI обновление → нарратив.

## 6.2. Задачи

- Реализовать `AvailableAction`.
- Реализовать `PlayerActionRequest`.
- Реализовать action validation.
- Реализовать Rules Engine v0:
  - d6 dice pool;
  - основные/временные/ситуационные модификаторы;
  - difficulty;
  - margin;
  - critical success/fail.
- Реализовать deterministic/auditable dice log.
- Реализовать первый шаблон сцены.
- Реализовать `SystemResultBlock`.
- Реализовать `DiceResultPanel`.
- Реализовать `NarrativeBlock` с mock AI.
- Реализовать fallback narration без внешнего LLM.
- Реализовать один простой enemy encounter.
- Реализовать выдачу одной награды через транзакцию.

## 6.3. Deliverables

- Игрок может выполнить первое действие в сцене.
- Сервер считает d6-проверку.
- UI показывает системный результат и нарратив отдельно.
- Event log сохраняет действие.
- Dice log сохраняет бросок.

## 6.4. Критерии завершения

- Клиент не может выполнить action, которого нет в available actions.
- ИИ/mock narration не может добавить награду.
- Повтор action request не дублирует награду.
- Результат действия понятен игроку без чтения логов разработчика.

# 7. Фаза 4 — первый этаж MVP

## 7.1. Цель

Собрать первый этаж как играбельную MVP-зону без глобального босса и сложного PvP.

## 7.2. Контент первого этажа

Реализовать:

- Рассветный Порог;
- Дорогу Пастухов;
- Светлую Опушку;
- базовый источник рассветника;
- несколько NPC;
- первые задания;
- первые враги;
- простую карту этажа;
- базовую хронику первого этажа.

## 7.3. Классы

Реализовать базовые архетипы на минимальном уровне:

- Мечник;
- Страж;
- Разведчик;
- Лучник;
- Маг;
- Целитель;
- Ремесленник.

Для MVP у каждого класса должны быть:

- стартовое описание;
- 1–2 базовых действия;
- роль в группе;
- хотя бы один out-of-combat акцент;
- UI-карточка класса.

## 7.4. Инвентарь и крафт

Реализовать:

- рассветник;
- простое зелье лечения;
- базовый инвентарь;
- stackable items;
- расход предмета;
- крафтовый рецепт;
- проверку требований крафта;
- транзакционную выдачу результата.

## 7.5. Deliverables

- Игрок может пройти стартовый маршрут.
- Игрок может собрать рассветник.
- Игрок может скрафтить зелье.
- Игрок может провести простой PvE-бой.
- Игрок видит карту первого этажа.

## 7.6. Критерии завершения

- Первый этаж можно пройти в соло 15–30 минут.
- Нет свободного ввода команд.
- Все награды идут через серверные транзакции.
- Все важные действия пишутся в event log.
- Крафт не допускает отрицательные остатки.

- Реализовать wallet/item transactions.
- Реализовать reconciliation job.
- Реализовать базовый рынок или NPC-торговлю, в зависимости от MVP scope.
- Реализовать ремонт/расход durability, если входит в MVP.
- Реализовать лимиты добычи рассветника.

## 9.3. Contested route задачи

- Реализовать Тропу Рассветника как contested zone.
- Добавить PvP warning modal.
- Добавить whitelist PvP-действий.
- Добавить защиту новичков.
- Добавить лимит потерь.
- Добавить cooldown повторного нападения.
- Добавить флаг агрессора.
- Записать PvP-события в event log и ledger.
- Добавить безопасную альтернативу с меньшей выгодой.

## 9.4. Deliverables

- Рассветник имеет безопасный и спорный источник.
- Спорная зона явно предупреждает игрока.
- Ограниченный грабёж работает только по правилам.

## 9.5. Критерии завершения

- Нельзя ограбить игрока вне разрешённой зоны.
- Нельзя забрать больше лимита.
- Нельзя атаковать защищённого новичка.
- Ledger сходится с фактическим состоянием инвентарей.
- Повтор PvP-запроса не повторяет грабёж.

- Спорный PvP-инцидент можно восстановить по логам.
- Экономический дюп можно обнаружить и расследовать.
- Ошибочное действие можно отключить без деплоя, если оно data-driven.
- Support не требует прямого доступа к БД для базовых операций.

# 12. Фаза 9 — Closed alpha

## 12.1. Цель

Проверить ядро игры на небольшой группе игроков до публичного запуска.

## 12.2. Масштаб

Рекомендуемый размер:

- 20–100 игроков;
- 1–2 недели первого раунда;
- несколько коротких playtest-сессий;
- отдельный Discord/форма обратной связи;
- reset/wipe допустим и заранее объявлен.

## 12.3. Что проверять

- Понимают ли игроки, что это не чат с ИИ.
- Понимают ли игроки доступные действия.
- Понятна ли d6-система.
- Не путают ли игроки нарратив и системные результаты.
- Не пугает ли UI сложностью.
- Работает ли первый сбор/крафт.
- Не вызывает ли contested route чрезмерный негатив.
- Нет ли дюпов.
- Не ломается ли realtime.
- Сколько стоит LLM narration, если включена реальная модель.

## 12.4. Deliverables

- Alpha report.
- Список критических багов.
- Список UX-проблем.
- Список балансных проблем.
- Решение: продолжать, повторить alpha или срезать scope.

## 12.5. Критерии завершения

- Нет критических дюпов.
- Нет массовой путаницы из-за запрета свободного ввода.
- Первый gameplay loop понятен большинству игроков.
- PvP первого этажа не вызывает массовый churn.
- Стоимость ИИ на игрока понятна.

# 13. Фаза 10 — Public beta

## 13.1. Цель

- Настройка PvP-лимитов.
- Настройка классовых действий.
- Улучшение mobile UX.

## 13.4. Метрики beta

- первое действие → первый бой;

## 13.5. Критерии завершения

- Экономика не ломается за несколько дней.

# 17. Риск-реестр

| Риск | Вероятность | Ущерб | Mitigation |
|---|---:|---:|---|
| ИИ начнёт восприниматься как источник правил | Средняя | Высокий | Жёсткое UI-разделение Narrative/System, schema validation, запрет free-text commands |
| d6-система станет слишком сложной | Средняя | Средний | Progressive disclosure, DiceResultPanel, симуляции, onboarding |
| Экономика сломается из-за дюпа | Средняя | Критический | Ledger, idempotency, constraints, reconciliation jobs |
| PvP отпугнёт новичков | Средняя | Высокий | Только один contested route, лимиты, защита новичков, понятные warnings |
| Realtime будет нестабилен | Средняя | Высокий | Deep Research, нагрузочные тесты, reconnect UX, state recovery |
| Первый этаж станет слишком большим для MVP | Высокая | Средний | Scope freeze, MoSCoW, vertical slice first |
| Контент будет сложно производить | Средняя | Высокий | Content schemas, templates, admin tools, staged publish |
| Стоимость LLM станет высокой | Средняя | Средний | Mock/fallback, caching, budget limits, cheap model routing |
| Топ-гильдии монополизируют босса | Средняя | Высокий | Contribution caps, windows, catch-up, anti-sabotage rules |
| Нет инструментов поддержки | Средняя | Высокий | Admin/observability до public beta |

# 22. Go / No-Go критерии

## 22.1. Go к closed alpha

- Работает первый gameplay loop.
- Нет известных критических дюпов.
- Есть базовая админка/log view.
- Есть понятный onboarding.
- Есть fallback без LLM.
- Есть сбор обратной связи.

## 22.2. Go к public beta

- Closed alpha не выявила критический пересмотр core loop.
- Realtime стабилен на тестовой нагрузке.
- Экономика проходит reconciliation.
- PvP ограничен и логируется.
- Support может расследовать инциденты.
- Есть публичные правила теста.

## 22.3. Go к launch

- Backup/restore проверены.
- First kill flow проверен на staging.
- Нет критических exploit-цепочек.
- Метрики и алерты работают.
- Команда готова к live support.
- Есть контентный план на первые недели.
